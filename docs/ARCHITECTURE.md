# Architecture

이 문서는 "무엇을 만들었는가"보다 **"왜 그렇게 했는가"**를 남긴다. 코드가 스스로
설명하는 부분은 생략한다.

## 1. 스택과 그 이유

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| Framework | Next.js 16 (App Router) | Server Component + Server Action으로 API layer 없이 서버에서 직접 읽고 쓴다. 1인 개발에서 유지할 표면이 줄어든다. |
| DB | **Neon** (serverless Postgres) | Supabase slot 부족에 대한 대안. 진짜 Postgres이므로 스키마 설계가 그대로 살아있고, 나중에 pgvector도 붙는다. |
| ORM | Drizzle | 스키마가 곧 TypeScript 타입. migration이 검토 가능한 SQL 파일로 남는다. |
| Auth | 자체 세션 (jose + bcrypt) | 아래 §3 참조 |
| SRS | `ts-fsrs` | 검증된 FSRS 구현. 간격 규칙을 직접 만들지 않는다. |
| Styling | Tailwind v4 | 토큰을 CSS에 두고 색을 상태 표현에만 쓴다. |

### Supabase를 쓰지 않으면서 잃은 것과 메운 방법

| Supabase 기능 | 대체 |
| --- | --- |
| Postgres | Neon (동일) |
| Auth | 자체 세션 (§3) |
| Row Level Security | Application layer 인가 (§4) |
| Storage | MVP에 파일 업로드 없음. 필요해지면 Vercel Blob 또는 Cloudflare R2 |
| Edge Functions | Next.js Route Handler / Server Action |
| Cron | 현재 불필요 (§5) |

**이식성**: Neon 고유 기능은 쓰지 않는다. 연결 문자열 하나가 유일한 결합점이므로
Supabase slot이 나면 그때 옮겨도 된다.

## 2. 가장 중요한 경계: Master vs Personal

```
Master Brain Map  = WHAT THE WORD IS      (공용, 검수됨, 단어당 1개)
Personal Brain Map = HOW THIS STUDENT KNOWS IT (학생별, 검수 대상 아님)
```

이 둘은 테이블도, 읽기 경로도, 캐시 특성도 다르다.

- `brain_maps` 와 그 자식 테이블 — 학생이 몇 명이든 단어당 한 벌
- `user_vocabulary_cards`, `brain_map_node_progress`, `user_confusions` — 학생별

`getMasterBrainMap()` 과 `getPersonalBrainMap()` 은 별도 함수이고, 화면을 그릴 때만
`getBrainMapView()` 에서 합쳐진다. 이 분리가 §6의 공용 지식 베이스를 가능하게 한다.

## 3. 인증

Auth.js v5는 오랫동안 beta이고, 이 서비스에는 social login 요구가 없다. 과외
선생님이 학생 계정을 만들어 주는 사용 방식에는 이메일+비밀번호로 충분하다.

그래서 `src/lib/auth/` 에 최소 세션을 직접 구현했다. 약 150줄이고, 바꿔 끼우기
쉽도록 그 디렉터리 밖으로 새지 않는다.

쿠키에는 사용자 정보가 아니라 **`sessions` row에 대한 서명된 참조**만 담는다.
요청마다 인덱스 조회가 한 번 더 들지만, "이 학생을 모든 기기에서 로그아웃" 이
DELETE 한 줄이 된다.

## 4. 인가 — RLS를 쓰지 않는 이유

Postgres RLS는 요청마다 별도 role로 연결할 때만 실제로 구속력이 있다. serverless
환경의 pooled connection에서는 이게 번거롭고, 어설프게 설정하면 **켜져 있는데
동작하지 않는** 최악의 상태가 된다.

대신 모든 교사 측 읽기가 `assertCanAccessStudent()` 한 곳을 지나가게 했다.
`teacher_student_links` 에 active row가 없으면 어떤 학생 데이터에도 닿을 수 없다.
학생 자신의 데이터는 세션의 `actor.id` 로만 조회한다 — 클라이언트가 보낸 id는
어떤 경로에서도 신뢰하지 않는다.

이 선택의 대가는 **규율**이다: 새 쿼리를 추가할 때 이 게이트를 우회하면 아무도
막아주지 않는다. 그래서 `tests/authorization.test.ts` 가 8가지 경우를 고정한다.

향후 팀이 커지거나 직접 DB 접근이 생기면 RLS를 추가로 켜는 것이 맞다. 스키마는
그때를 위해 이미 `user_id` 기준으로 정규화되어 있다.

## 5. Retention

`ts-fsrs` 에 위임한다. 이 모듈이 하는 일은 하나뿐이다: **UI가 모으는 정답/오답 +
응답 시간을 FSRS가 원하는 4단계 등급으로 변환**하는 것.

```
오답                          → Again
정답이지만 느림 (>12s)        → Hard
정답                          → Good
정답이고 빠름 (<3.5s), Review → Easy
```

`Easy` 를 새 카드에 주지 않는 이유: 처음 본 단어를 빨리 맞히는 것은 오래 기억한다는
증거가 아니다.

### 저장하지 않는 것

`estimated_retention` 은 **컬럼으로 두지 않는다.** 시간이 지나면 계속 변하므로
저장하는 순간 틀린 값이 된다. `(stability, 경과 시간)` 에서 읽을 때 계산한다.

### 방향별 카드

`(user, vocabulary, direction)` 마다 카드가 하나씩이다. `maintain → 유지하다` 를
안다는 것이 `유지하다 → maintain` 을 안다는 뜻은 아니기 때문이다. due queue 조회가
`WHERE user_id = ? AND due_at <= now()` 하나로 끝나는 부수 효과도 있다.

### Cron이 필요 없는 이유

다음 복습 시각은 답변 시점에 계산되어 `due_at` 에 저장된다. queue는 "지금보다
`due_at` 이 이른 카드"를 읽기만 하면 되므로, 배치로 밀어줄 것이 없다. 알림을
붙이는 시점에 Vercel Cron을 도입하면 된다.

## 6. 공용 지식 베이스

서비스의 장기 자산이다. 이를 지키는 장치는 세 가지다.

1. **`vocabularies_natural_key`** — `(lower(lemma), language, part_of_speech)` unique.
   `findOrCreateVocabulary()` 가 유일한 writer다.
2. **`brain_maps.vocabulary_id` unique** — 단어당 Master Map은 하나뿐.
3. **`ai_jobs_inflight_unique`** — `status in ('pending','running')` 인 job에 대한
   partial unique index. 두 학생이 같은 단어를 동시에 건드려도 생성은 한 번만 돈다.

교사가 학생에게 100개를 넣으면 이미 아는 87개는 기존 Map을 그대로 쓰고 13개만
생성된다. 이 동작은 UI에서 실제로 확인된다("새 단어 2개, 기존 단어 재사용 2개").

### 혼동 단어 짝을 top-level에 둔 이유

`word_pairs` 는 특정 Brain Map의 자식이 아니라 독립 엔티티다. "maintain vs keep"은
대칭이고 양쪽 단어에서 모두 도달해야 하기 때문이다. lemma를 정렬해 저장하므로
`keep vs maintain` 도 같은 row가 된다. 차이 설명과 문제를 한 벌만 관리한다.

## 7. AI 생성

```
AI = Creator   →   Teacher/Admin = Curator   →   Student = Learner
```

학생이 단어를 누를 때마다 LLM을 호출하지 않는다. 생성은 교사/관리자만 트리거할 수
있고, 결과는 `draft_ai` 로 들어가 **승인 전까지 학생에게 보이지 않는다.**

### 품질 통제

1. **구조화 출력** — Anthropic은 tool use, OpenAI는 json_schema. prose 덩어리를 DB에
   넣지 않는다.
2. **zod 검증** — 배열 길이 상한이 있다. Brain Map의 가치는 선별에 있다.
3. **교차 검증** (`validateDraftConsistency`) — 스키마가 표현할 수 없는 것들:
   `highlight` 가 문장 안에 실제로 있는지, 예문들이 서로 다른 용법인지, 빈칸이 정확히
   하나인지.
4. **빈 배열 허용** — 모델에게 "반드시 채워라"라고 하지 않는다. 없는 파생어를
   지어내는 것이 비어 있는 것보다 나쁘다.

`prompt_version` 과 `generated_by_model` 을 모든 Map에 남기므로, 나중에 품질 문제가
생기면 어느 프롬프트가 만든 것인지 추적하고 선별 재생성할 수 있다.

### 비용

실측: 입력 약 1,600 토큰(system 406 + 프롬프트 61 + tool schema 1,136), 출력 본문
약 1,160 토큰. **비용을 지배하는 것은 thinking 토큰**이다 — 출력으로 과금되고,
effort 설정에 따라 수 배로 움직인다.

`LLM_EFFORT` 가 그 조절 손잡이다. API 기본값은 `high` 이지만, Brain Map 생성은 스키마와
검증이 뒤를 받치는 경계가 뚜렷한 작업이라 기본을 `medium` 으로 낮춰 두었다. 초안 품질이
아쉬우면 올리면 된다.

tool schema와 system 프롬프트는 매 호출 바이트 단위로 동일하고 합쳐서 최소 캐시
프리픽스를 넘기므로, system 블록에 캐시 breakpoint를 두어 입력의 대부분을 1/10 가격에
읽는다. 다만 출력이 비용을 지배하므로 절감폭은 10% 안팎이다.

**한 단어당 한 번만 낸다.** 검수된 Map은 모든 학생이 공유하므로, 단어 수가 곧 총비용이고
학생 수는 비용에 영향을 주지 않는다.

### 버전 관리

`brain_map_revisions` 에 JSONB snapshot을 append한다. 자식 테이블 6개를 전부
temporal versioning하는 것은 이 규모에서 과하다. "N번 버전이 어땠고 누가 바꿨는가"에
답할 수 있으면 충분하다.

**Map을 수정해도 학생 학습 기록은 지워지지 않는다.** `review_events` 와
`brain_map_node_progress` 는 콘텐츠가 아니라 `vocabulary_id` 를 참조하기 때문이다.

## 8. Brain Map 확장 판단

`src/lib/learning/brain-map-policy.ts` — DB를 모르는 순수 모듈.

세 부류로 나눈다.

- **known** — 이미 아는 단어. 빠르게 통과.
- **memorise** — 약하지만 이해 문제는 아님. 반복 출제.
- **understand** — 확장 추천.

`understand` 가 되는 조건:

- 사람이 지정 (교사/학생/시험) → **즉시**. 세 번 틀릴 때까지 기다릴 이유가 없다.
- lapse ≥ 3, 또는 최근 8회 정답률 < 60%
- 유사어 / 문장 해석 / 연어 문제에서 2회 이상 오답

추천은 **끈적하게(sticky)** 유지된다. 학생이 Map을 열기 전까지 사라지지 않는다.
켜졌다 꺼졌다 하는 추천은 없느니만 못하다.

## 9. UI 판단

### 그래프 라이브러리를 쓰지 않았다

Brain Map은 CSS transform 기반 radial layout이다. 노드 5개의 각도가 고정이므로
계산할 layout이 없고, resize에 다시 그릴 것이 없으며, 360px에서도 읽히고 눌린다.
force-directed 그래프는 더 인상적이고 폰에서 더 나쁘다.

**색은 상태만 표현한다.** 회색=콘텐츠 없음, 파랑=학습 가능/중, 빨강=약함, 초록=완료.

### 맵 노드는 카테고리가 아니라 어휘 자체다

처음에는 Meaning / Sentences / Similar / Collocations / Family 다섯 개를 같은 크기로
방사형 배치했다. 그건 지도가 아니라 **메뉴**였다. 메뉴는 "무엇이 중요한가"도
"내가 어디가 약한가"도 말하지 못한다.

지금 노드에 가장 크게 적힌 글자는 언제나 실제 어휘다 — `issue vs problem`,
`raise an issue`, `문제, 쟁점`. 카테고리명은 작은 eyebrow 태그로만 남는다.

중요도는 범례 없이 읽혀야 하므로 **크기·중심으로부터의 거리·연결선 굵기**로 함께
인코딩한다(`src/lib/learning/map-layout.ts`). 배치는 황금각 + 노드 id 해시 지터로
계산해 정다각형이 되지 않게 하고, 겹침은 완화 패스로 푼다. 단어마다 결과가 항상
같아 방문할 때마다 지도가 재배열되지 않는다.

**중요도와 숙련도는 다른 축이다.** "문제, 쟁점"은 이미 완료여도 여전히 가장 중요한
노드이고, `issue vs problem`은 학생이 실제로 틀리고 있을 때 중요도가 최고가 된다.
전자는 콘텐츠의 성질, 후자는 학생의 상태다.

### 항목별 상태는 이벤트 로그에서 유도한다

`brain_map_node_progress` 는 다섯 카테고리 단위로만 집계한다. 노드가 어휘 단위가
되면서 항목별 상태가 필요해졌지만, **테이블을 새로 만들지 않았다.** `review_events`
는 append-only이고 payload에 이미 항목 id가 들어 있어서, 읽을 때 집계하면 된다.
마이그레이션 없이 더 세밀한 그림을 얻는 대신 읽기 비용을 조금 낸다.

### 노드는 보여주기가 아니라 활동이다

- 예문 — 먼저 직접 해석하고 나서 확인한다. 번역이 이미 보이는 문장을 읽는 것은
  학습이 아니다.
- 유사어 — 목록이 아니라 차이를 묻는 문제.
- 파생어 — 실제 시험 기능이 형태 판별이므로 그것을 묻는다.

콘텐츠가 없는 노드는 `locked` 로 렌더된다. 빈 노드로 학생을 초대하지 않는다.

### 시험 범위가 표로 올 때

단어장은 "1. govern / v. 통치하다 / * 예문"으로 오지만, 시험 범위는 표로 온다 —
어휘 / 영영 풀이 / 의미, 한 줄에 한 단어, 예문은 한 줄도 없다. 그 표를 줄 형식
파서에 넣으면 단어를 하나도 못 읽고 첫 줄에서 멈춘다.

표는 **열 위치가 아니라 칸의 내용으로 읽는다.** 번호를 붙이는 표도 있고 안 붙이는
표도 있으며, 열 순서는 선생님이 친 대로다. 믿을 수 있는 것은 각 칸이 *무엇인가*
뿐이다.

- 숫자만 있는 칸 → 행 번호, 버린다
- 품사 마크를 뗀 뒤 한글이 남으면 → 의미
- 남은 영어 칸 중 **짧은 쪽이 단어, 긴 쪽이 풀이**

마지막 규칙이 `sign up` / `to agree to take part in an organized activity` 를 어느
열이 어느 열인지 듣지 않고도 바르게 가른다. `in front of`, `according to` 처럼
여러 낱말인 표제어에서도 성립한다.

영어 품사 마크는 **점을 요구한다**(`v.`, `adj.`). 이 표의 어휘에서 `a` 는 형용사
마크이기도 해서, 점을 요구하지 않으면 `a large number or amount of people or
things` 가 형용사 + `large number or amount…` 로 잘린다. 책은 `v.` 를 점과 함께
쓰고 `명·동·형` 은 점 없이 쓰므로, 점을 요구하는 데 드는 비용은 없고 유일한
모호함이 사라진다.

마크다운 파이프와 탭 둘 다 읽는다. 같은 표가 문서에서는 `| a | b |` 로, 스프레드
시트에서는 탭으로 붙여넣어지기 때문이다. 파이프가 한 줄에만 있으면 표로 보지
않는다 — 나머지가 줄 형식인 붙여넣기를 파이프 하나 때문에 버릴 이유가 없다.

### 맵은 배우는 곳, 시험은 묻는 곳

같은 영영 풀이라도 두 화면에서 하는 일이 다르다.

**맵에서는 읽는다.** 영어 풀이가 카드에 놓이고, 그 해석은 누르기 전까지 나오지
않는다. 영어를 읽고 무슨 말인지 알아내는 것이 공부이고, 옆에 한국어가 붙어 있는
순간 공부가 아니게 된다. 예문 해석과 같은 모양이다 — 원래 여기서 유일하게 문제가
아니라 읽기였던 것.

**나오는 것은 그 문장의 해석이지 단어 뜻이 아니다.** "장점, 강점"은 `strength` 에
대해 참이지만, 학생이 "a quality or ability that gives you an advantage" 를 제대로
읽었는지에 대해서는 아무 말도 하지 않는다. 게다가 그 글자는 이미 옆 맵에 적혀
있다. 그래서 `brain_map_meanings` 에 `en_definition_ko` 를 뒀다 — 단어의 뜻(`ko`)과
풀이의 해석은 다른 것이고, 한 칸에 둘을 담을 수 없다.

**해석이 없으면 이 카드를 주지 않는다.** 단어 뜻을 대신 내놓는 것은 확인해 주는 것이
없는 확인 버튼이다 — `움직임, 동작` 은 맵에도, 위 제목에도, 들어온 목록에도 이미
적혀 있다. 대신 묻는다: 이 뜻의 영영 풀이는 넷 중 어느 것인가. 어느 쪽이든 시치미
떼지 않고, 노드가 비지도 않는다.

### 해석을 모델이 채운다 — 앱에서 돈을 쓰는 유일한 버튼

선생님의 목록은 영영 풀이와 단어 뜻은 찍어도 **풀이의 해석은 거의 안 찍는다.** 쉰
줄을 손으로 옮기는 것이 그 카드가 안 눌리게 되는 이유이므로, 교사 화면에서 한 번에
마흔 개씩 채운다(`fillDefinitionReadings`).

발음기호를 뺀 판단과 어긋나지 않는다. 그것은 선생님만 보는 것에 돈이 드는 자리였고,
이것은 **학생이 실제로 읽는 텍스트**다. 그리고 검수된 맵은 모두가 공유하므로 비용은
단어 수를 따르지 응시 학생 수를 따르지 않는다(§7).

**답을 번호로 짝짓는다.** 모델이 하나를 빠뜨리거나 순서를 바꿔도 `goal` 의 해석이
`dot` 에게 가면 안 된다.

**막아야 할 실패는 하나뿐이고 길이로는 안 잡힌다** — 모델이 풀이의 해석 대신 단어
뜻을 돌려주는 것. "a small round mark" 에 대한 "점" 은 훌륭한 한국어이고 완전히
쓸모없는 답이다. 이미 옆 맵에 적혀 있기 때문이다. 그래서 `cleanReading` 은 우리가
이미 가진 뜻과 대조해 그 경우를 버린다.

선생님이 표에 해석 열을 직접 넣었으면 그것이 이긴다. 채우기는 비어 있는 칸에만
쓴다.

### 한국어 열이 둘이면 표 제목 줄이 필요하다

표는 칸의 내용으로 읽는다 — 열 순서를 약속받지 않아도 되니까. 그 방법이 통하지
않는 경우가 하나 있다: **한국어 열이 둘일 때.** 단어의 뜻과 풀이의 해석은 둘 다
한국어이고, 어느 쪽이 어느 쪽인지 글자 안에 단서가 없다.

그래서 제목 줄이 있으면 그것을 믿고 열을 자리로 읽는다(`readHeader`). 없으면
기존대로 내용으로 읽고, 두 번째 한국어 칸은 뜻의 일부로 이어 붙인다 — 짐작하지
않는다.

그 카드의 제목은 **단어**다. 카드는 늘 학습 중인 항목을 머리에 찍는데, 의미 노드의
그것은 한국어 뜻이고, 그 뜻을 감추는 것이 목적인 카드에서 그것은 답을 굵게 적어
둔 것이 된다.

**시험에서는 고른다.** 넷 중 맞는 풀이를 고르는 것도 좋은 문제다. 다만 그것은
공부가 아니고, 옆에 맵이 없는 화면의 몫이다.

### 맵 시험의 한쪽 방향이 굶고 있었다

맵 시험은 목록의 방향을 그대로 물려받고, 기본은 `en_ko` 다. 그런데 그 방향에는
변형이 **하나**뿐이었고, 그 하나는 단어에 뜻이 둘 있고 그중 하나를 보여주는 예문이
있어야 성립했다. 영영 풀이로만 된 범위는 둘 다 없다 — 그래서 모든 단어가 평범한
영한 문제로 떨어졌고, 맵 시험은 "단어 수만 적은 보통 시험"이 되어 있었다.

나누는 기준은 **무엇을 떠올리는가**다. 답이 영어면 `ko_en`, 한국어면 `en_ko`.

| 방향 | 맵에서 나오는 문제 |
| --- | --- |
| `en_ko` | 이 문장에서의 뜻 · 이 표현의 뜻 · 이 파생어의 뜻 |
| `ko_en` | 문맥 속 빈칸 · 함께 쓰는 표현 · 알맞은 형태 |
| 양쪽 | **영영 풀이에 맞는 단어** |

### 영영 풀이의 답은 언제나 단어다

한 문제만 방향 규칙을 벗어난다. 일부러 그렇다.

영영 풀이 문제는 처음에 두 벌이었다 — 풀이를 주고 단어를 묻는 쪽(`ko_en`)과 풀이를
주고 한국어 뜻을 묻는 쪽(`en_ko`). 시험은 기본적으로 `en_ko` 로 열리므로, 실제로
학생 앞에 놓인 것은 뒤쪽이었다. **시험지가 내는 문제는 앞쪽이다.**

뒤쪽은 문제로서도 약하다. 풀이를 읽고 나서 고르는 것이 그 단어 옆에 어차피 늘 적혀
있는 뜻이라면, 그것은 긴 지문을 붙인 평범한 영한 문제다.

그래서 한 벌만 남기고 양쪽 방향에 둔다. 영어 풀이를 읽고 영어 단어를 떠올리는 것은
어느 카드가 재는 것보다 어려운 일이고, `ko_en` 에만 두면 방향 토글을 한 번도 건드리지
않은 학생은 그 문제를 영영 만나지 못한다.

### 영영 풀이가 문제가 되는 이유

이런 범위에는 예문이 없으므로 배치할 문맥도 없고, 지금까지 맵은 카드 한 장에
"문제가 준비되지 않았어요"만 띄웠다.

카드가 이미 찍지 않는 유일한 것이 **영영 풀이**다. 그래서 그것을 묻는다.

```
'장점, 강점' — 이 뜻의 영영 풀이는?
```

오답은 **같은 세트 다른 단어들의 풀이**다. 함께 시험지에 오르는 단어들이고, 그것을
가려내는 것이 곧 시험이다(`listRivalDefinitions`). 세트가 없는 단어는 라이브러리가
뒤를 받친다.

반대로 물으면 문제가 아니다 — 단어는 맵 한가운데 적혀 있다. 그 방향은 맵이 없는
화면, 즉 시험 세션의 몫이다: 영영 풀이를 주고 단어를 고르게 하며, 오답은 같은
세트에서 나온다. 시험지가 내는 문제 그대로다.

### 50단어를 넣는 데 850번 오간 이유

단어 하나를 넣는 데 왕복이 열일곱 번 든다. 찾고, 넣고, 뜻을 넣고, 맵의 머리와
부품 전부를 트랜잭션 안에서 넣는다. 그것을 쉰 번 이어 붙이면 **854번이 한 줄로
늘어선다.** 같은 기계 위의 DB에서는 0.7초지만, 세 홉 건너에 있는 DB에서는 왕복
50ms × 854 ≈ 43초다. "만드는 중…" 만 뜬 채로 그만큼이다.

단어끼리는 서로에게 기대는 것이 없다. 그러니 그 기다림은 순수한 지연이고, 겹치는
것이 곧 해결이다(`src/lib/import/batches.ts`). 폭은 짐작이 아니라 **연결 풀의
너비**다 — 풀은 열 개를 쥐고 각 단어의 쓰기는 트랜잭션 동안 하나를 잡으므로, 더
달라고 해도 빨라지지 않고 남는 질의가 DB 대신 클라이언트에서 기다린다.

실제 50단어 범위로 재니 **가장 깊은 연결이 854문장에서 117문장**이 됐다. 총
문장 수는 그대로다 — 줄인 것은 일이 아니라 줄서기다.

### 오래 걸리는 일은 오래 걸린다고 말해야 한다

겹쳐도 몇 초다. 그 몇 초 동안 "만드는 중…" 만 있는 버튼은 멈춘 버튼과 구별되지
않는다. 서버 액션은 브라우저에 진행률을 줄 수 없으므로 — 요청이 열려 있다가 닫힐
뿐이다 — 정직하게 말할 수 있는 것은 **얼마를 시켰고 시간이 흐르고 있다**는 두
가지뿐이다. 버튼 아래에 "단어 50개를 넣고 있어요 · 6초"가 흐른다.

### 저장 전 미리보기는 사실만 말해야 한다

붙여넣기 화면은 단어마다 무엇을 읽었는지 세어 보여준다. 그것이 잘못 읽힌 붙여넣기가
드러나는 유일한 자리이므로, 세는 항목과 경고가 실제와 어긋나면 안 된다.

시험 범위 표를 넣었을 때 `예문 0 · 연어 0 · 파생어 0 · 예문 없음` 이 떴다. 앞의
셋은 사실이지만 — 표에는 정말 없다 — **읽어 들인 영영 풀이는 세지 않았고, 경고는
틀렸다.** 예문이 문제의 유일한 재료이던 때의 규칙이 남아, 곧 잘 동작할 50개 단어
전부에 "문제 없음"을 붙이고 있었다. 붙여넣은 사람이 파싱이 실패했다고 읽은 것이
맞다.

`영영` 을 세는 항목에 넣고, 경고는 **정말 낼 문제가 없을 때만** 붙인다 —
`draftHasQuestions`. 영영 풀이는 붙여넣기 안의 다른 풀이와 겨루어야 문제가 되므로,
그 판단은 단어가 아니라 붙여넣기 전체에 대한 사실이다.

### 언어를 말하는 것과 목소리를 고르는 것은 다르다

`SpeechSynthesisUtterance.lang` 은 **텍스트가 무슨 언어인지**를 말한다. 그것을 읽을
목소리를 고르지는 않는다. 브라우저는 그래도 기본 목소리를 쓸 수 있고, 한국어 기기의
기본은 한국어 목소리다. 그래서 앱의 모든 영어 단어가 한국어 소리로 읽혔다 —
`strength` 가 "스트렝쓰"로. 엔진은 시킨 대로 했을 뿐이고, 영어 목소리를 달라고 한
적이 없었다.

고르는 규칙은 `src/lib/learning/voices.ts` 에 순수 함수로 있다. 소리로만 확인되는
버그이고 테스트를 돌리는 기계에는 목소리가 하나도 없으므로, 규칙만이라도 고정할 수
있어야 했다.

**빈 목록은 "영어 목소리가 없음"이 아니다.** `getVoices()` 는 첫 호출에 비어 있다가
나중에 채워지는 일이 흔하므로 둘을 구분한다. 목소리가 있는데 그중 영어가 없는
기기에서만 스피커 버튼을 감춘다 — 스트렝쓰라고 읽는 버튼은 없는 버튼보다 나쁘고,
그것은 작동하지 않는 버튼을 그리지 않는 것과 같은 이유다.

### 발음기호를 뺀 이유, 음성을 남긴 이유

발음기호(IPA)를 보는 사람은 과외 선생님뿐이었고 학생은 보지 않았다. 그런데 그것을
채우는 유일한 경로가 모델 호출이었다 — 단어장 파서도 책이 `[kəntémpərèri]` 를 찍어
두면 읽게 돼 있지만, 실제 단어장 20개 중 0개였다. 아무도 안 보는 것에 유일하게 돈이
드는 자리였으므로 뺐다.

**음성 재생은 남는다.** `SpeakButton` 은 브라우저 자체 음성 합성이라 비용도 네트워크
왕복도 없고, 애초에 발음기호를 필요로 하지 않았다. "어떻게 읽는지 모르겠다"에 답하는
것은 기호가 아니라 소리다.

`vocabularies.pronunciation` 컬럼은 선언만 남겼다. 살아 있는 DB에 이미 있고, 지우면
적혀 있던 값만 잃는다. 스키마에서 빼면 다음 `drizzle-kit generate` 가 바로 그
DROP 마이그레이션을 제안한다.

### 정답은 화면에 적혀 있으면 안 된다

문제 카드는 언제나 **지금 학습 중인 항목을 문제 바로 위에** 크게 찍고, 뒤의 맵이
같은 글자를 한 번 더 보여준다. 처음 만든 문제들은 그 사실을 계산에 넣지 않았다.

| 노드 | 물었던 것 | 카드 맨 위에 적혀 있던 것 |
| --- | --- | --- |
| 함께 쓰는 표현 | `raise an issue` 의 빈칸 — 마지막 단어 `issue` | `raise an issue` |
| 파생어 | 문장 속 `maintenance` | `maintenance` |
| 핵심 의미 | 이 문장의 뜻은 뜻 목록 중 어느 것인가 | `문제, 쟁점` |

정답이 위에 적혀 있는 물음은 문제가 아니다. 다섯 종류 중 셋이 그랬고, 그것이
맵의 문제가 사소하게 느껴진 이유다.

그래서 **방향을 뒤집었다.** 항목은 답이 아니라 주어진 값이고, 묻는 것은 그것이
**어디에 들어가는가**이다.

```
'사회적 쟁점'    — 이 뜻으로 쓰인 문장은?     (후보: 그 단어의 다른 뜻으로 쓰인 문장들)
'raise an issue' — 어느 문장에 들어갈까요?    (후보: 다른 표현의 예문, 전부 빈칸 처리)
'issue'          — 어느 문장에 들어갈까요?    (후보: issue 자리와 problem 자리)
```

화면의 어떤 글자도 이 물음에 답해 주지 않고, 답하려면 후보를 실제로 읽어야 한다.
그 다음 문제는 그 문장을 해석하는 것이고, 그것도 라벨이 알려줄 수 없다.

같은 규칙이 노드 안의 순서도 정한다. **앞 문제가 뒤 문제의 답을 흘리면 안 된다.**
배치 문제는 정답 문장의 한국어를 피드백으로 찍으므로, 해석할 문장은 배치 후보에서
빼 둔다. 뺄 문장이 없으면(그 뜻의 예문이 하나뿐이면) 피드백이 번역 대신 "나머지
문장은 무슨 쓰임이었는지"를 말한다.

혼동 단어 노드만 예외적으로 두 후보를 라벨에 다 적는다(`issue vs problem`). 어느
쪽인지는 여전히 말하지 않으므로, 이 노드는 양방향으로 물을 수 있다.

### 문제는 큐레이터가 쓴 구분을 그대로 쓴다

`issue` 의 예문 중 둘은 뜻이 `문제, 쟁점` 이다 — 사회적 쟁점 하나, 개인적 이견
하나. 노드 라벨(`문제, 쟁점`)로 물으면 정답이 둘이 된다. 그래서 문제는 노드
라벨이 아니라 **그 문장에 적힌 `target_meaning`** 으로 묻는다(`사회적 쟁점`).
답은 하나가 되고, 물어지는 구분은 큐레이터가 적어 둘 만하다고 판단한 바로 그
구분이다.

`meanings.ko` 와 `sentences.target_meaning` 은 서로 맞춰 쓰이지 않는다 —
`(기계·건물을) 정비하다, 관리하다` 와 `기계를 정비하다` 는 같은 쓰임의 다른
표기다. 문자열이 같은지로 묶으면 `maintain` 의 핵심 의미에 예문이 하나도 붙지
않는다. 그래서 **두 글자 이상인 단어를 공유하는지**로 묶는다. 어긋나면 배치 문제
하나를 잃을 뿐, 노드가 비지는 않는다.

### 이미 맞힌 항목에는 입구를 다시 내주지 않는다

배치 문제는 시작하는 방법이다. 이미 맞힌 학생에게 그것을 또 내는 것은 "이 항목
완료" 화면을 한 단계 늘린 것에 지나지 않는다. 그 노드에는 해석 문제만 남는다 —
남길 것이 그것뿐일 때만 배치 문제가 그대로 있는다.

### 단어장에서 온 항목

책은 표현과 뜻만 찍고 예문을 주지 않는다. 배치할 문맥이 없으므로, 카드가 이미
보여주지 않는 유일한 것 — **뜻** — 을 묻는다. 후보는 그 단어의 다른 표현들의
뜻이고, 그것이 책 자체가 내는 문제다. 대조할 것이 하나도 없으면 문제를 만들지
않는다.

### 학생에게 숨기는 것

`stability`, `difficulty`, SRS interval은 노출하지 않는다. 대신 "기억 안정도:
높음/보통/위험", "다음 복습 3일 후".

## 10. 요구사항에 대한 반론

요청받은 것 중 의도적으로 다르게 한 부분들이다.

**`estimated_retention` 을 컬럼으로 두지 않았다.**
매초 변하는 값이므로 저장하는 순간 낡는다. `stability` 와 `difficulty` 만 저장하고
읽을 때 계산한다. UI가 보는 값은 항상 정확하다.

**`vocabulary_meanings` 를 별도 사전 테이블로 만들지 않았다.**
Brain Map의 `meaning_core` 와 병렬로 두면 같은 정보가 두 곳에 생기고 반드시
어긋난다. 뜻은 `brain_map_meanings` 하나에 두고, recall용 한국어 gloss만
`vocabulary_translations` 로 분리했다. 역할이 다르기 때문이다.

**Brain Map 전체를 temporal versioning하지 않았다.**
자식 테이블 6개에 유효기간을 다는 것은 1인 운영에서 과하다. append-only JSONB
snapshot으로 충분하다.

**Teacher 기능은 스키마만 갖추고 UI는 최소로 했다.**
Class/Group, Assignment 만료, Analytics 대시보드는 테이블과 관계만 준비했다.
학생이 실제로 붙기 전에 만들면 틀린 것을 만들게 된다.

**pgvector / Vector DB — 넣지 않았다.** (요청과 같은 결론)
수천 단어 규모에서 Postgres prefix index가 1ms 안에 답한다. 실제 semantic search
요구가 생기기 전에는 도입할 이유가 없다.

**Cloudflare Workers / R2 / Vectorize — 넣지 않았다.** (요청과 같은 결론)
지금 해결하는 문제가 없다.

## 11. 테스트가 고정하는 것

`pnpm test` — 355개. 순수 로직은 DB 없이, 나머지는 `TEST_DATABASE_URL` 이 있을 때만.

의도적으로 다음을 고정한다.

- FSRS 등급 매핑과 간격 증가, 오답 시 lapse와 streak 초기화
- 확장 정책의 세 부류, 사람 지정의 즉시성, 노드 상태 파생
- **어떤 문제의 정답도 그 노드의 label과 같지 않다** — seed 3단어와 단어장 4단어
  전부에 대해. 이 규칙이 무너지면 맵의 문제는 다시 베껴 쓰기가 된다
- 연어 빈칸이 목표 단어가 아닌 쪽에 뚫리는지, 후보가 전부 빈칸 처리되는지
- 앞 문제가 뒤 문제의 답을 흘리지 않는지 (해석할 문장은 배치 후보에서 빠진다)
- 이미 맞힌 항목에 1단계 문제가 다시 나오지 않는지
- AI 출력 스키마: 빈 배열 허용, 길이 상한, 알 수 없는 필드 제거, 교차 검증
- **손으로 쓴 seed Brain Map이 AI와 똑같은 검증을 통과하는지** — seed가 품질 기준이므로
- 단어 중복 방지 (대소문자, 공백, 품사 동음이의어, 품사 없음)
- Master Map 재사용: 두 번째 요청은 생성하지 않음, 동시 요청은 한 번만 생성,
  실패 시 lock 해제
- 짝이 양쪽 단어에서 같은 row인지
- 학생 간 상태 격리
- 교사 접근 게이트 8가지 경우

- 마이그레이션 파일과 `meta/_journal.json` 이 어긋나지 않는지

### 마이그레이션은 배포가 돌린다

파이프라인에 그 단계가 없었다. 스키마를 바꿀 때마다 Neon 콘솔에 SQL을 손으로
붙여야 했고, `en_definition_ko` 는 그 컬럼이 없는 데이터베이스를 향해 배포됐다.
Brain Map을 읽는 모든 화면이 서버 오류로 답했고, 파이프라인의 무엇도 알아채지
못했다 — 아무것도 보고 있지 않았으니까.

이제 **배포 전에** 돌린다. 여기의 마이그레이션은 무언가를 더하기만 하므로(널 가능
컬럼, 새 테이블), 돌아가고 있는 코드는 그것을 무시하고 새 코드는 결코 먼저 도착하지
않는다. 연결 문자열이 없으면 배포를 **막는다** — 컬럼이 있는지 모르는 데이터베이스를
향해 코드를 내보내는 것이 방금 겪은 그 실패다.

Neon의 pooled 연결은 마이그레이션이 잡는 advisory lock을 쥐지 못하므로 직접 연결이
필요하다 — 호스트에 `-pooler` 가 **없는** 쪽.

**`db:migrate` 와 `schemaStatus` 는 서로 다른 것을 본다.** 전자는 기록 테이블을,
후자는 실제 컬럼을. 기록은 있는데 컬럼이 없으면 마이그레이션은 건너뛰고 상태만
"오래됨"으로 남는다 — 그때는 손으로 그 한 줄을 돌리는 수밖에 없다. 두 눈이 서로
다른 곳을 보는 것은 의도된 것이고(§아래), 어긋날 수 있다는 것도 그 대가다.

### "다음"은 어느 목록의 다음인가

단어 화면은 옆으로 넘겨 다음 단어로 간다. 그 "다음"은 **들어온 목록의** 다음이고,
목록에서 들어오지 않았다면 아무 의미가 없다.

세트를 달아 주는 진입점은 세트 단어 목록 하나뿐이었다. 복습 화면에서, 시험 결과
화면에서, 선생님의 학생 페이지에서 — 전부 단어에만 링크했다. 그렇게 열린 화면에서
이웃은 **라이브러리 전체를 알파벳순으로** 계산됐고, 50개짜리 세트 안에서 옆으로
넘기면 그대로 다른 세트의 단어로 걸어 나갔다. 폰에서 보이는 모습이 정확히 그것이다:
한 세트에서 다음 세트로 넘어감.

세트가 없다는 것만으로는 답이 안 된다 — 라이브러리 목록에도 세트는 없다. 그래서
**목록이 링크할 때 그렇게 말한다**(`from=list`). 그 표시가 없으면 이웃을 아예 읽지
않고 페이저도 그리지 않는다. 쿼리 하나를 아끼는 것은 덤이다.

담은 단어 목록은 목록이지만 표시를 달지 않는다. `wordNeighbours` 가 재현하는 순서가
그 목록의 순서가 아니어서, 거기 페이저를 달면 라이브러리를 넘기게 된다 — 잘못된
페이저보다 없는 편이 낫다.

### 한 화면에 스크롤은 하나뿐이어야 한다

단어 목록은 한 화면을 넘기면 자기 안에서 스크롤하게 돼 있었다. 아래의 페이저와
버튼이 제자리에 남게 하려는 것이었는데, 폰에서는 정확히 반대로 작동했다.

그 상자는 화면 폭만큼 넓다. 손가락은 언제나 그 위에 있고, `overscroll-contain` 은
바로 그 스크롤이 페이지로 이어지는 것을 막는 규칙이다. 목록은 스물다섯 번째
단어에서 끝나고, 그 아래의 `1 / 2` 에 닿으려면 상자 옆 몇 픽셀의 여백을 찾아
잡아야 했다. **50개짜리 세트가 25개짜리로 읽히는 이유가 이것이다.**

태블릿부터는 옆에 여지가 있어 의도대로 동작했다. 필요 없던 곳에서만 동작하는
규칙은 그것이 망가뜨리는 폰만큼의 값어치도 없다.

같은 자리에서 숫자 둘이 서로 다른 말을 하고 있었다. 탭은 `전체 50`, 한 줄 아래
목록 머리는 `25개`. 작은 쪽이 단어들 옆에 있는 숫자다. 이제 자기가 전체의 어느
부분인지 말한다 — `25개 / 전체 50`.

### 화면이 실패할 때 학생이 보는 것

프레임워크의 오류 페이지는 검은 화면과 영어 한 문장과 숫자 하나다. 학생이 할 수
있는 일을 말해주지 않고, 1초 전까지 쓰던 앱처럼 보이지도 않는다.

`(app)/error.tsx` 가 정직한 오류 화면이 늘 말하는 세 가지를 말한다: 무언가 잘못됐다,
당신 탓이 아니다, 돌아가는 길은 이쪽이다. digest는 남긴다 — Worker 로그에서 어느
실패였는지 잡는 유일한 손잡이이고, 그래서 작게 맨 아래에 있다. 우리를 위한 것이지
학생을 위한 것이 아니므로.

### 저널에 없는 마이그레이션은 조용히 건너뛴다

`drizzle-kit generate` 는 `.sql` 과 저널 항목을 같이 쓰지만, 손으로 쓴
마이그레이션은 파일만 생긴다. 실행기는 저널을 읽으므로 그런 파일은 **성공을
보고하면서 실행되지 않는다.** `0002_pronunciation.sql` 이 그렇게 며칠 동안 존재만
했고, 그 사이에 `pnpm db:migrate` 나 `db/setup.sql` 로 만든 DB에는
`vocabularies.pronunciation` 이 없다.

고칠 때 지킨 것: SQL은 `ADD COLUMN IF NOT EXISTS` 로 두어 컬럼을 손으로 이미 넣은
DB가 깨지지 않게 하고, 저널의 `when` 은 마지막 적용분보다 뒤로 잡아 이미 0001까지
온 DB에서도 적용되게 했다. 새 DB / 옛 setup.sql로 만든 DB / 컬럼을 손으로 넣은 DB
세 경우를 로컬 Postgres에서 실제로 돌려 확인했다 — 어느 쪽도 데이터를 잃지 않는다.

`tests/migrations.test.ts` 가 이 어긋남을 고정한다. 실패가 조용하기 때문이다.

이 컬럼은 지금 아무것도 읽지 않는다(아래 "발음기호를 뺀 이유"). 그래도 마이그레이션은
그대로 둔다 — 이미 적용된 DB가 있고, 되돌리는 마이그레이션은 얻는 것 없이 저장된
값만 버린다.

### 테스트 DB 격리

테스트는 모든 테이블을 truncate한다. 그래서 `TEST_DATABASE_URL` 만 읽고, DB 이름에
`test` 가 없으면 실행을 거부한다. (개발 중 실제로 개발 DB를 날려서 추가한 안전장치다.)
